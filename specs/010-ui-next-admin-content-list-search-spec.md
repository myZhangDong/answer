# 010 `ui-next` 后台内容列表搜索 Spec

## 1. 背景

当前 `ui-next` 管理后台已经补齐了文章、视频、项目的列表、新建、编辑、删除闭环，但三类内容列表的搜索能力仍不一致，影响日常运营检索效率。

现状问题主要有三类：

- 文章列表当前只支持按标签筛选，不支持关键字搜索
- 视频列表和项目列表当前只支持分页浏览，页面上明确提示“后续补统一搜索”
- 前台搜索页虽然存在“综合搜索”，但当前实现是分别拉取文章、视频、项目列表后在前端本地过滤，不适合作为后台分页列表搜索方案

同时，仓库内虽然已有 `/answer/api/v1/search` 通用搜索接口，但它仍是旧社区搜索体系，目标类型还是 `all/question/answer`，并不适合直接承载 `ui-next` 后台文章、视频、项目三类内容管理列表的搜索。

因此需要拆出 `010` 独立规格，先固定以下口径：

- 后台三类内容列表搜索都以各自分页列表接口为准
- 视频、项目优先复用现有后端 `search` 参数能力
- 文章补最小后端搜索能力，不额外引入新的独立搜索接口
- 三类列表统一 URL 状态和交互方式，避免后续每页各写一套

## 2. 目标

### 2.1 产品目标

让 `ui-next` 管理后台的文章、视频、项目列表具备可用且一致的关键字搜索能力。

第一阶段必须满足：

- 文章列表支持关键字搜索
- 视频列表支持关键字搜索
- 项目列表支持关键字搜索
- 三类列表的搜索交互、URL 参数和翻页行为保持一致
- 从列表进入编辑页或新建页再返回时，原搜索条件和页码可以保留
- 文章列表原有标签筛选能力继续保留，并可与关键字搜索同时生效

### 2.2 工程目标

在不引入新后台搜索中心、不改旧 `ui/` 的前提下，优先复用现有分页接口并补齐最小缺口。

工程约束：

- 第一阶段只改 `ui-next`
- 不复用前台综合搜索页的“前端拉全量后再过滤”方式
- 不直接把 `/answer/api/v1/search` 接到后台列表
- 视频、项目优先只做前端参数透传
- 文章只补最小必要的后端查询能力，不做全文检索体系改造

## 3. 非目标

本规格不做以下事情：

- 不改旧 `ui/` 后台列表页
- 不新增一个“后台综合搜索页”
- 不把三类内容合并成一个统一列表搜索接口
- 不做文章正文全文检索、标签全文检索或作者维度高级检索
- 不新增排序维度、批量操作或高级筛选器
- 不改前台 `/search` 页面实现
- 不改用户、标签管理之外的其他后台页面搜索交互

## 4. 现状确认

### 4.1 文章列表当前只有标签筛选，没有关键字搜索

当前 `ui-next/src/app/pages/AdminArticles.tsx` 已支持：

- 分页
- 标签筛选
- 新建、编辑、删除

但页面当前仍明确提示“当前优先支持按标签筛选”，没有关键字输入框和提交动作。

同时，文章列表调用的 `getAdminArticles` 仍走 `/answer/api/v1/content/page`，只传：

- `page`
- `page_size`
- `order`
- `content_type=2`
- `tag`

现有后端 `ContentPageReq` 和 `GetContentPage` 也没有 `search` 字段和关键字过滤逻辑。

结论：

- 文章后台搜索不能只改前端
- 需要对 `/answer/api/v1/content/page` 补最小搜索能力

### 4.2 视频和项目列表后端已具备搜索参数能力

当前后端已支持：

- `GET /answer/api/v1/video/page?search=...`
- `GET /answer/api/v1/project/page?search=...`

现有 schema 和 repo 已有搜索字段与 SQL 条件：

- 视频按 `title`、`description` 模糊匹配
- 项目按 `title`、`description` 模糊匹配

但 `ui-next/src/app/api/adminApi.ts` 的后台列表请求尚未把关键字参数透传到这两个接口。

结论：

- 视频、项目后台搜索第一阶段以“前端补输入框 + URL 状态 + 参数透传”为主
- 不需要额外新开视频、项目搜索接口

### 4.3 前台综合搜索不能直接复用于后台列表

当前 `ui-next/src/app/pages/Search.tsx` 的实现是：

- 并行请求文章、视频、项目列表
- 每类内容默认只拉固定条数
- 在前端内存里做本地过滤

这不满足后台列表搜索要求，因为它存在以下问题：

- 不是服务端分页搜索
- 会漏掉未被预拉取的内容
- 无法与后台列表当前页码保持一致
- 无法自然复用文章标签筛选和后台返回逻辑

结论：

- 后台三类内容列表不复用前台综合搜索页实现
- 后台三类内容列表继续以自己的分页接口为唯一数据源

### 4.4 旧社区 `/search` 接口不是本轮复用目标

仓库内的 `/answer/api/v1/search` 仍面向旧社区搜索体系，目标对象主要是：

- question
- answer
- all

它不直接面向：

- 视频
- 项目
- 内容门户后台运营列表

结论：

- 本轮不把 `/answer/api/v1/search` 接到 `ui-next` 后台内容列表
- 后台内容搜索继续围绕列表分页接口做最小扩展

## 5. 关键边界

### 5.1 三类列表统一使用 `query` 作为前端 URL 参数名

第一阶段统一约定：

- 地址栏查询参数统一使用 `query`
- 页面内部搜索输入框草稿值从 `query` 初始化
- 点击搜索按钮或按回车后，把 `query` 写入 URL
- 只要搜索条件变化，页码统一重置为 `page=1`
- 清空搜索时，从 URL 删除 `query`

这样做的目的不是引入新后端参数，而是让三个页面在前端路由层拥有一致的状态模型。

### 5.2 前端 `query` 与后端接口 `search` 解耦

前端统一使用：

- `query`

后端接口继续沿用各自现有或新增的：

- `search`

映射关系为：

- 页面从 URL 读 `query`
- 前端 API 层把 `query` 映射为请求参数 `search`

影响：

- 前端路由状态可统一
- 后端接口不需要为了 `ui-next` 再改一套入参命名

### 5.3 文章列表搜索第一阶段只做标题模糊匹配

文章列表本轮新增的后端搜索能力，第一阶段只约束为：

- 基于文章标题做模糊匹配

不包含：

- 文章正文全文检索
- 标签名称模糊检索
- 作者名模糊检索
- `article:123` 这类特殊语法搜索

原因：

- 当前文章仍建立在 `question(content_type=2)` 链路上
- `content/page` 当前职责是列表分页，不适合在这一轮演化成完整全文检索入口
- 标题搜索已能满足后台日常定位大部分内容的诉求

### 5.4 文章标签筛选与关键字搜索允许同时生效

文章列表第一阶段允许：

- `tag`
- `query`

同时存在。

组合规则固定为：

- 标签条件与关键字条件是 `AND` 关系

即：

- 先限定标签范围
- 再在结果里应用标题关键字匹配

影响：

- 不需要让运营在“标签筛选”和“关键字搜索”之间二选一
- 页面返回后可保留更精确的上下文状态

### 5.5 搜索交互采用显式提交，不做输入时实时请求

第一阶段统一采用：

- 回车触发搜索
- 点击按钮触发搜索

不做：

- 输入时逐字请求
- debounce 自动搜索

原因：

- 后台运营搜索频率相对可控
- 当前三类列表已经有分页和 URL 状态逻辑，显式提交更稳妥
- 可减少无意义请求和状态抖动

### 5.6 列表返回路径必须保留搜索和页码状态

第一阶段要求：

- 列表进入编辑页时，继续通过当前 `location.search` 透传返回信息
- 编辑页保存、取消或返回后，应回到带原 `query` 和 `page` 的列表地址

影响：

- 搜索不能只存在局部 `useState`
- 需要继续依赖 `useSearchParams` 作为页面状态事实来源

### 5.7 范围先收口到 `ui-next` 和必要的文章后端补口

第一阶段只改：

- `ui-next/src/app/pages/AdminArticles.tsx`
- `ui-next/src/app/pages/AdminVideos.tsx`
- `ui-next/src/app/pages/AdminProjects.tsx`
- `ui-next/src/app/api/adminApi.ts`
- 文章列表搜索所需的最小后端 schema / service / repo / controller 透传链路

不改：

- 旧 `ui/`
- 前台 `/search`
- 视频、项目后端搜索语义
- 后台其他管理模块

## 6. 验收标准

第一阶段完成后，应满足：

- 文章列表支持关键字搜索，且可与标签筛选同时生效
- 视频列表支持关键字搜索
- 项目列表支持关键字搜索
- 三类页面都使用统一的 `query` URL 参数保存搜索状态
- 搜索后翻页、返回编辑页再回列表时，搜索状态不会丢失
- 清空搜索后可回到默认列表
- 视频、项目继续复用现有分页接口，不新增额外后端搜索接口
- 文章搜索不复用 `/answer/api/v1/search`，而是在 `/answer/api/v1/content/page` 上补最小能力
- `ui-next` 构建通过，且文章、视频、项目列表原有分页与删除回流逻辑不回归
