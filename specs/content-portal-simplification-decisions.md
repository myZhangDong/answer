# 内容门户化改造 Decisions

## 使用方式

这份文档只记录三类信息：

- 已确认的产品或工程决策
- 仍未确认但会影响后续实施的开放问题
- 当前阶段的最近检查点

如果某个判断已经会影响后续实现，应先写入这里，再继续改码。

## 已确认决策

### D-001 继续基于现有项目改造，不新写一个项目

状态：已确认

原因：

- 现有后端、后台、视频和项目能力已经具备可复用基础
- 直接重写项目成本更高，也会丢失已有管理能力和数据链路

影响：

- 后续策略以“收口和裁剪”为主
- 第一轮不追求彻底删除所有社区模块

### D-002 新前端以 `ui-next/` 为主，不再以 `ui/` 作为目标前台

状态：已确认

原因：

- 新设计已经在 Figma 完成，并已生成可运行前端代码
- `ui-next/` 已经包含当前前台页面和管理后台页面

影响：

- 前台替换以 `ui-next/` 为主线推进
- `ui/` 在迁移阶段主要作为旧实现参考和兼容来源

### D-003 前台产品范围只保留三类内容

状态：已确认

范围：

- 热门文章
- 视频教程
- 开源项目

影响：

- 不再把 Questions、Users、Badges、Review 作为前台产品能力
- 标签仅作为文章聚合能力考虑，不再扩展成社区标签系统

### D-004 只有管理员可登录并发布内容

状态：已确认

影响：

- 前台不再暴露普通用户注册、登录、个人中心
- 后台继续保留管理员登录与内容发布链路
- 第一轮默认继续复用现有后台鉴权，不立即重写认证体系

### D-005 文章点赞和评分不再绑定普通用户

状态：已确认

影响：

- 后续要改为匿名或弱身份统计
- 这部分属于后续阶段，不阻塞当前 UI 与内容收口

### D-006 Phase 0 先让 `ui-next/` 跑通并接现有后端接口

状态：已确认

影响：

- 替换旧前端之前，先保证新前端可运行、可取数
- 现阶段先复用现有文章、视频、项目接口，不先做后端大裁剪

### D-007 文章详情与管理后台预览默认复用同一套 Markdown 渲染思路

状态：已确认

说明：

- `ui-next/` 中文章详情和后台编辑区都已围绕 `MarkdownRenderer` 和 `CodeBlock` 组织
- 当前不在本轮引入新的代码高亮组件替换现有实现

影响：

- 先保证内容能正确渲染
- 高亮效果优化可以放到后续独立任务

### D-008 Phase 1 保留前台搜索，但只服务内容门户

状态：已确认

影响：

- 前台可继续保留搜索入口
- 搜索结果应收敛为文章、视频、项目三类内容
- 后续裁剪时不再保留社区导向的搜索范围

### D-009 标签不保留独立社区页，只保留文章聚合能力

状态：已确认

影响：

- 标签只服务文章筛选、展示和相关文章能力
- 后续不再把旧 `Tags` 页面当作内容门户正式页面保留

### D-010 Phase 1 后台基线继续以旧 `ui/` 为生产可用后台

状态：已确认

原因：

- 旧 `ui/` 已接通现有登录与后台管理能力
- `ui-next` 的 `adminApi` 仍是 stub，尚未对接真实接口和认证

影响：

- 本轮继续复用现有管理员登录和旧后台页面
- 后续若迁移后台到 `ui-next`，应单独作为明确任务执行

### D-011 文章当前仍是 `question(content_type=2)` 的兼容实现

状态：已确认

影响：

- 文章详情、创建、编辑和公开列表仍然依赖 `question` 相关接口
- 后续 Phase 5 以前，不应假设文章已经具备完全独立的后端模型和 API

### D-012 `ui-next` 管理员登录与后台鉴权迁移拆分为独立规格

状态：已确认

原因：

- 内容门户主规格的重点是前台收口与产品边界，不适合继续混放后台认证迁移细节
- 当前 `ui-next` `/admin` 仍是演示密码门，和旧 `ui/` 真实认证链路差异较大，需要单独约束

影响：

- 后续涉及 `ui-next` 管理员登录、会话恢复、后台路由守卫时，优先读取 `specs/ui-next-admin-auth-spec.md`
- `ui-next` 后台认证默认继续复用现有后端接口 `/answer/api/v1/user/login/email`、`/answer/api/v1/user/info`、`/answer/api/v1/user/logout`
- 管理员准入判定继续沿用旧 `ui/` 语义，即 `role_id === 2`

### D-013 `ui-next` 管理员登录独立规格按默认值推进

状态：已确认

默认值：

- 第一轮只支持邮箱 + 密码管理员登录
- `captcha`、User Center、Connector 登录适配先列为兼容项
- 第一轮只实现认证骨架、会话恢复、退出登录、后台路由守卫、请求层会话复用
- `ui-next` 使用显式 `/admin/login` 路由
- 非管理员访问 `ui-next /admin` 时返回 `403`
- 旧 `ui/` 后台继续保留为迁移期间 fallback

影响：

- 可以直接按 `specs/ui-next-admin-auth-tasks.md` 拆分和执行，无需再次等待范围确认
- 插件接管型登录与验证码 UI 适配不作为第一轮阻塞项

### D-014 `ui-next` 文章后台第一阶段继续复用 `question(type=2)` 写接口

状态：已确认

原因：

- 当前后端文章创建仍复用 `/answer/api/v1/question`
- 后端真实可写字段仍以标题、正文、标签为主
- `ui-next` 当前设计稿中的作者、发布日期、封面、摘要并没有一一对应的独立文章写接口

影响：

- `ui-next` 文章后台第一阶段直接提交 `title`、`content`、`tags` 和 `type=2`
- 标签继续复用现有 `/answer/api/v1/question/tags` 查询后端已有标签
- 作者沿用当前登录管理员身份语义
- 封面、摘要、发布日期暂不作为独立后端字段写入，后续如需正式支持应单独补后端模型或扩展写接口

### D-015 内容审核增加后端配置开关，默认保持开启

状态：已确认

原因：

- 本地开发和联调阶段，文章创建会被真实内容审核拦截，影响后台录入链路验证
- 直接删除审核逻辑会改变线上默认行为，不适合当前阶段

影响：

- 后端通过 `service_config.disable_content_review` 控制是否跳过内容审核
- 默认值保持 `false`，即线上和默认环境继续开启审核
- 本地开发环境需要绕过审核时，可在配置文件中显式设为 `true`

### D-016 `ui-next` 项目后台第一阶段显式暴露 `question_id` 录入

状态：已确认

原因：

- 当前后端项目创建接口 `POST /answer/api/v1/project` 强依赖 `question_id`
- 现阶段不改后端模型，不额外引入“项目先建内容再自动补关联”的新流程

影响：

- `ui-next` 项目后台创建页需要显式填写关联文章 ID
- 项目编辑页继续展示已关联的 `question_id`，但不允许修改
- 如果后续希望移除该字段，需要单独改后端项目创建链路

### D-017 Phase 2 的前台收口先在 `ui-next` 执行，旧 `ui/` 暂不裁剪

状态：已确认

原因：

- 当前新前端主线已经明确为 `ui-next`
- 旧 `ui/` 仍承担参考实现和迁移期 fallback 角色
- 过早同步裁剪旧前端会扩大改动面，不利于当前联调节奏

影响：

- Phase 2 的前台路由、导航、Header、CTA 收口优先只改 `ui-next`
- 旧 `ui/` 本轮保持现状，不做同步删除或菜单裁剪
- 后续如果要正式下线旧前端，再单独做一次针对 `ui/` 的收口

### D-018 `003` 网站设置迁移第一阶段范围已确认

状态：已确认

已确认范围：

- `ui-next` 第一阶段迁移旧后台的 `general`、`interface`、`branding`、`seo`
- `ui-next` 第一阶段新增首页运营位配置，覆盖首页顶部 Banner 和“周热门文章”上方广告位
- 首页顶部区域按“图片 + 链接”的 Banner 实现，直接替换当前硬编码 Hero 区块
- “周热门文章”广告位未配置时直接不显示，不保留默认素材 fallback
- `ui-next` 管理后台导航从顶部改为左侧，并尽量与前台导航风格保持一致

影响：

- 后续实现 `003` 时，不需要再为 `seo`、Banner 形态和广告位空态单独等待确认
- 首页顶部 Banner 不再沿用当前 `Home.tsx` 的固定文案 Hero 结构
- `ui-next` 后台壳子需要调整为左侧导航布局，不能只是在现有顶部标签上追加“网站设置”

### D-019 `003` 后续扩展优先迁移纯表单型站点设置，暂缓高耦合项

状态：已确认

原因：

- 用户已确认“现在前端能支持的功能也有必要的就可以迁移”
- 旧后台 `login`、`legal`、`custom-css-html` 属于纯表单配置，迁到 `ui-next` 的实现成本和联调风险更低
- `write` 依赖标签选择、文件限制等专用交互，`themes` 依赖旧主题体系，当前都不适合直接硬搬到 `ui-next`

影响：

- `003` 后续如果继续扩展，默认优先级按 `legal -> login -> custom-css-html`
- `write` 需等 `ui-next` 补齐专用标签/限制配置交互后再迁移
- `themes` 不默认纳入当前迁移批次，除非后续明确要让 `ui-next` 重新消费旧主题配置

### D-020 `003` 同步纳入后台用户管理迁移，不保留旧后台顶部筛选形态

状态：已确认

原因：

- 当前内容门户运营需要在 `ui-next` 里直接添加其他管理员账号，不能继续依赖单一管理员
- 旧 `ui/` 的用户后台已具备成熟接口，`ui-next` 迁移成本主要在页面和交互层
- 用户已明确表示旧后台顶部筛选功能不是必需项

影响：

- `003` 后续范围扩展为：用户列表、添加账号、编辑资料、修改角色、修改状态、设置新密码
- `ui-next` 用户管理页不必复刻旧 `ui/` 顶部 tabs，可改为更轻量的搜索 + 下拉范围切换
- 用户管理继续复用现有后端接口 `/answer/admin/api/users/page`、`/answer/admin/api/user`、`/answer/admin/api/user/role`、`/answer/admin/api/user/status`、`/answer/admin/api/user/password`、`/answer/admin/api/user/profile`、`/answer/admin/api/roles`

### D-023 `004` 匿名互动改为单 token 单次提交

状态：已确认

已确认细节：

- 同一匿名 `token` 对同一内容对象只能点赞一次
- 同一匿名 `token` 对同一内容对象只能评分一次，不再支持后续覆盖旧评分
- 详情页需要能读取当前匿名访客是否已点赞、是否已评分以及自己的评分值

影响：

- 后端点赞接口从“重复提交幂等”收口为“重复提交直接拒绝”
- 后端评分接口从“允许覆盖”收口为“首次提交后不可再次修改”
- 匿名互动读取接口需要补当前访客操作态字段，前端据此禁用按钮和星级输入

### D-024 `004` 前端以 `localStorage` 固化游客单次互动状态

状态：已确认

已确认细节：

- 同一游客对同一内容对象允许进行 1 次点赞和 1 次评分，两者分别独立限制
- 游客完成点赞后写入点赞状态，完成评分后写入评分状态
- 页面刷新或重新进入详情页后，仍按本地持久化状态禁用互动入口

影响：

- 前端详情页不能只依赖服务端返回的 `liked_by_me` / `rated_by_me`
- `LikeAndRating` 需要分别控制点赞按钮和评分交互的禁用态
- 页面进入时需要合并服务端状态与本地持久化状态

### D-025 `004` 详情页交互顺序按“先赞后评”收口

状态：已确认

已确认细节：

- 游客点赞后，点赞按钮禁用，但仍可继续评分一次
- 游客评分后，评分入口禁用，同时点赞按钮也禁用
- 如果游客已经完成“点赞 + 评分”，当前页应立即同时禁用两个入口，不能等到离开页面后才生效

影响：

- 点赞按钮禁用条件应为 `liked_by_me || rated_by_me`
- 评分入口禁用条件应为 `rated_by_me`
- 详情页提交成功后的本地状态更新需要按“保留已完成动作”方式合并，不能直接用单次响应覆盖

### D-026 `005` 文章标签管理第一阶段至少覆盖创建、编辑、删除

状态：已确认

原因：

- 当前后台没有标签管理入口时，文章录入链路不完整
- 只做“列表 + 创建”不足以支撑基础运营维护

影响：

- `ui-next` 需要新增文章标签管理页

- 如复用后端现有能力，恢复标签和标签描述维护可以同轮补齐
