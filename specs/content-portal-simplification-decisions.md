# 内容门户化改造 Decisions

## 使用方式

这份文档只记录三类信息：

- 已确认的产品或工程决策
- 仍未确认但会影响后续实施的开放问题
- 当前阶段的最近检查点

如果某个判断已经会影响后续实现，应先写入这里，再继续改码。

## 已确认决策

### D-001 继续基于现有项目改造，不新写一个项目

状态：已确认

原因：

- 现有后端、后台、视频和项目能力已经具备可复用基础
- 直接重写项目成本更高，也会丢失已有管理能力和数据链路

影响：

- 后续策略以“收口和裁剪”为主
- 第一轮不追求彻底删除所有社区模块

### D-002 新前端以 `ui-next/` 为主，不再以 `ui/` 作为目标前台

状态：已确认

原因：

- 新设计已经在 Figma 完成，并已生成可运行前端代码
- `ui-next/` 已经包含当前前台页面和管理后台页面

影响：

- 前台替换以 `ui-next/` 为主线推进
- `ui/` 在迁移阶段主要作为旧实现参考和兼容来源

### D-003 前台产品范围只保留三类内容

状态：已确认

范围：

- 热门文章
- 视频教程
- 开源项目

影响：

- 不再把 Questions、Users、Badges、Review 作为前台产品能力
- 标签仅作为文章聚合能力考虑，不再扩展成社区标签系统

### D-004 只有管理员可登录并发布内容

状态：已确认

影响：

- 前台不再暴露普通用户注册、登录、个人中心
- 后台继续保留管理员登录与内容发布链路
- 第一轮默认继续复用现有后台鉴权，不立即重写认证体系

### D-005 文章点赞和评分不再绑定普通用户

状态：已确认

影响：

- 后续要改为匿名或弱身份统计
- 这部分属于后续阶段，不阻塞当前 UI 与内容收口

### D-006 Phase 0 先让 `ui-next/` 跑通并接现有后端接口

状态：已确认

影响：

- 替换旧前端之前，先保证新前端可运行、可取数
- 现阶段先复用现有文章、视频、项目接口，不先做后端大裁剪

### D-007 文章详情与管理后台预览默认复用同一套 Markdown 渲染思路

状态：已确认

说明：

- `ui-next/` 中文章详情和后台编辑区都已围绕 `MarkdownRenderer` 和 `CodeBlock` 组织
- 当前不在本轮引入新的代码高亮组件替换现有实现

影响：

- 先保证内容能正确渲染
- 高亮效果优化可以放到后续独立任务

### D-008 Phase 1 保留前台搜索，但只服务内容门户

状态：已确认

影响：

- 前台可继续保留搜索入口
- 搜索结果应收敛为文章、视频、项目三类内容
- 后续裁剪时不再保留社区导向的搜索范围

### D-009 标签不保留独立社区页，只保留文章聚合能力

状态：已确认

影响：

- 标签只服务文章筛选、展示和相关文章能力
- 后续不再把旧 `Tags` 页面当作内容门户正式页面保留

### D-010 Phase 1 后台基线继续以旧 `ui/` 为生产可用后台

状态：已确认

原因：

- 旧 `ui/` 已接通现有登录与后台管理能力
- `ui-next` 的 `adminApi` 仍是 stub，尚未对接真实接口和认证

影响：

- 本轮继续复用现有管理员登录和旧后台页面
- 后续若迁移后台到 `ui-next`，应单独作为明确任务执行

### D-011 文章当前仍是 `question(content_type=2)` 的兼容实现

状态：已确认

影响：

- 文章详情、创建、编辑和公开列表仍然依赖 `question` 相关接口
- 后续 Phase 5 以前，不应假设文章已经具备完全独立的后端模型和 API

### D-012 `ui-next` 管理员登录与后台鉴权迁移拆分为独立规格

状态：已确认

原因：

- 内容门户主规格的重点是前台收口与产品边界，不适合继续混放后台认证迁移细节
- 当前 `ui-next` `/admin` 仍是演示密码门，和旧 `ui/` 真实认证链路差异较大，需要单独约束

影响：

- 后续涉及 `ui-next` 管理员登录、会话恢复、后台路由守卫时，优先读取 `specs/ui-next-admin-auth-spec.md`
- `ui-next` 后台认证默认继续复用现有后端接口 `/answer/api/v1/user/login/email`、`/answer/api/v1/user/info`、`/answer/api/v1/user/logout`
- 管理员准入判定继续沿用旧 `ui/` 语义，即 `role_id === 2`

### D-013 `ui-next` 管理员登录独立规格按默认值推进

状态：已确认

默认值：

- 第一轮只支持邮箱 + 密码管理员登录
- `captcha`、User Center、Connector 登录适配先列为兼容项
- 第一轮只实现认证骨架、会话恢复、退出登录、后台路由守卫、请求层会话复用
- `ui-next` 使用显式 `/admin/login` 路由
- 非管理员访问 `ui-next /admin` 时返回 `403`
- 旧 `ui/` 后台继续保留为迁移期间 fallback

影响：

- 可以直接按 `specs/ui-next-admin-auth-tasks.md` 拆分和执行，无需再次等待范围确认
- 插件接管型登录与验证码 UI 适配不作为第一轮阻塞项

### D-014 `ui-next` 文章后台第一阶段继续复用 `question(type=2)` 写接口

状态：已确认

原因：

- 当前后端文章创建仍复用 `/answer/api/v1/question`
- 后端真实可写字段仍以标题、正文、标签为主
- `ui-next` 当前设计稿中的作者、发布日期、封面、摘要并没有一一对应的独立文章写接口

影响：

- `ui-next` 文章后台第一阶段直接提交 `title`、`content`、`tags` 和 `type=2`
- 标签继续复用现有 `/answer/api/v1/question/tags` 查询后端已有标签
- 作者沿用当前登录管理员身份语义
- 封面、摘要、发布日期暂不作为独立后端字段写入，后续如需正式支持应单独补后端模型或扩展写接口

### D-015 内容审核增加后端配置开关，默认保持开启

状态：已确认

原因：

- 本地开发和联调阶段，文章创建会被真实内容审核拦截，影响后台录入链路验证
- 直接删除审核逻辑会改变线上默认行为，不适合当前阶段

影响：

- 后端通过 `service_config.disable_content_review` 控制是否跳过内容审核
- 默认值保持 `false`，即线上和默认环境继续开启审核
- 本地开发环境需要绕过审核时，可在配置文件中显式设为 `true`

### D-016 `ui-next` 项目后台第一阶段显式暴露 `question_id` 录入

状态：已确认

原因：

- 当前后端项目创建接口 `POST /answer/api/v1/project` 强依赖 `question_id`
- 现阶段不改后端模型，不额外引入“项目先建内容再自动补关联”的新流程

影响：

- `ui-next` 项目后台创建页需要显式填写关联文章 ID
- 项目编辑页继续展示已关联的 `question_id`，但不允许修改
- 如果后续希望移除该字段，需要单独改后端项目创建链路

### D-017 Phase 2 的前台收口先在 `ui-next` 执行，旧 `ui/` 暂不裁剪

状态：已确认

原因：

- 当前新前端主线已经明确为 `ui-next`
- 旧 `ui/` 仍承担参考实现和迁移期 fallback 角色
- 过早同步裁剪旧前端会扩大改动面，不利于当前联调节奏

影响：

- Phase 2 的前台路由、导航、Header、CTA 收口优先只改 `ui-next`
- 旧 `ui/` 本轮保持现状，不做同步删除或菜单裁剪
- 后续如果要正式下线旧前端，再单独做一次针对 `ui/` 的收口
