# 内容门户化改造 Spec

## 1. 背景

当前项目源于 Apache Answer，原始定位是社区问答系统，天然包含：

- 普通用户注册、登录、找回密码、个人中心
- 问题、回答、评论、收藏、关注、通知、徽章、评审
- 管理后台中的用户、权限、站点配置、插件等能力

但当前业务方向已经收敛为一个内容门户站点，前台只保留三类内容：

- 热门文章
- 视频教程
- 开源项目

后台只保留管理员登录与内容发布能力，只有管理员能创建、编辑、删除文章、视频、项目。

因此需要把现有项目从“社区问答平台”收缩为“单管理员内容发布站”。

## 2. 目标

### 2.1 产品目标

前台用户只能浏览内容，不再面向普通访客开放社区交互。

保留的前台内容：

- 文章列表与文章详情
- 视频列表与视频详情
- 开源项目列表与项目详情
- 标签页仅作为文章筛选/聚合能力保留，不再作为社区标签体系对外扩展
- 搜索是否保留，作为可选项处理

保留的后台能力：

- 管理员登录
- 管理员发布/编辑/删除文章
- 管理员发布/编辑/删除视频
- 管理员发布/编辑/删除项目
- 站点基础配置、品牌、SEO、主题等能力按现状保留

调整的交互能力：

- 文章点赞、评分不再绑定普通用户身份
- 前台不再显示注册、登录、个人中心、通知、徽章、评审入口

### 2.2 工程目标

本轮改造优先做“收口”和“减法”，而不是一次性彻底删除所有历史社区代码。

执行原则：

- 第一阶段以隐藏入口、裁剪路由、限制 API 暴露为主
- 第二阶段再逐步收缩后端依赖和冗余模块
- 不在第一轮强行清除所有用户体系相关源码

## 3. 非目标

本次不做以下事情：

- 不重写为新项目
- 不立即彻底删除所有 question/answer/user/review/badge 代码
- 不在第一轮重做数据库整体结构
- 不重做整个后台框架，只做内容运营所需精简
- 不强制移除插件系统

## 4. 现状判断

从当前仓库可确认：

- 前台路由仍然包含 Questions、Users、Badges、Review、Search、Tags 等社区能力
- 前台导航仍然暴露 Questions、Tags、Users、Badges 等入口
- Header 仍然保留普通用户登录、注册、创建问题、通知等交互
- 后端 `internal/router/answer_api_router.go` 仍对外暴露大量社区 API
- 后端 `controller/service/repo` 仍围绕社区模型组织
- 视频、项目功能已经有较完整的前台与后台实现
- 文章能力已存在前台与创建能力基础

## 5. 目标状态

### 5.1 前台信息架构

前台主导航仅保留：

- 热门文章
- 视频教程
- 开源项目

可选保留：

- 搜索
- 标签聚合页

前台下线入口：

- 常见问题 / 问答首页
- 提问
- 回答编辑
- 用户列表
- 用户主页
- 用户设置
- 通知
- 徽章
- 评审
- 用户登录
- 用户注册
- 找回密码
- User Center / OAuth 前台入口

### 5.2 后台信息架构

后台第一阶段保留：

- Dashboard
- 文章管理
- 视频管理
- 项目管理
- Branding
- Interface
- SEO
- Theme
- CSS/HTML
- General
- Legal
- Login

后台待下线或隐藏：

- Questions
- Answers
- Users
- Privileges
- SettingsUsers
- Badges
- 与社区运营直接相关的页面

### 5.3 身份与权限

仅保留管理员登录作为可见入口。

工程上分两层处理：

- 第一阶段：继续复用现有鉴权体系，但前台不暴露普通用户登录注册，普通用户功能不再作为产品能力提供
- 第二阶段：按需要把后台认证收敛为更简单的管理员模型

说明：

- `ui-next` 管理员登录与后台认证迁移不再继续混在本规格内推进
- 相关实现边界单独见 `specs/ui-next-admin-auth-spec.md`

### 5.4 点赞与评分

点赞、评分不再与普通用户绑定。

建议方案：

- 改为匿名统计或弱身份统计
- 可按 `IP + UA + Cookie` 或设备 token 做去重
- 不要求登录
- 对前台只返回聚合计数，不展示“某用户是否点赞”

## 6. 实施策略

采用三阶段策略。

在正式裁剪旧前端之前，先完成 `ui-next/` 的独立运行和后端 API 接入，避免一边替换 UI 一边删除旧逻辑，导致问题难以定位。

### 阶段 0：新前端接入准备

目标：

- 让 `ui-next/` 可以独立运行
- 让 `ui-next/` 先接通当前后端可用接口
- 在不破坏现有 `ui/` 的前提下完成新旧前端并行验证

方法：

- 确认 `ui-next/` 的技术栈、构建输出、路由模式、环境变量方式
- 在 `ui-next/` 内建立 API 请求层
- 先对接文章、视频、项目的现有后端接口
- 先让核心页面跑通，再进入旧系统裁剪

说明：

- 当前 `ui-next/` 已确认是 `Vite + React` 项目，适合作为静态 SPA 接入现有 Go 后端
- 正式替换前，`ui-next/` 作为并行前端目录保留
### 阶段 A：新前端内容对接

目标：

- 让 `ui-next/` 的文章、视频、项目页面都能用真实后端数据运行
- 明确哪些旧接口可以直接复用，哪些需要补充适配

方法：

- 对接文章列表/详情 API
- 对接视频列表/详情 API
- 对接项目列表/详情 API
- 统一封装 `ui-next/` 的请求层和环境变量

### 阶段 B：产品收口

目标：

- 让前台和后台对外呈现为内容门户
- 不再让访客感知这是问答系统

方法：

- 清理前台路由
- 清理 Header / SideNav / MobileSideNav 入口
- 去掉普通用户登录注册按钮和页面跳转
- 收缩后台菜单，只保留内容管理项

说明：

- 如果推进 `ui-next` 后台接管管理员登录，不在本规格内展开实现细节
- 后台认证接入与会话复用以独立规格 `specs/ui-next-admin-auth-spec.md` 为准

### 阶段 C：接口收口

目标：

- 让后端仅暴露当前产品真正需要的 API

方法：

- 对外 API 白名单化
- 下线或内部化 question/answer/review/notification/badge/user-center 相关公开接口
- 将文章、视频、项目的管理操作改为管理员能力

### 阶段 D：模型简化

目标：

- 把点赞/评分从用户体系中解绑
- 清理不再需要的权限耦合

方法：

- 重构点赞/评分数据模型与接口
- 弱化 rank/permission 对内容站功能的参与
- 逐步收缩 provider 与 service 依赖

## 8. 关键设计决策

### 决策 1：不立即删除用户体系源码

原因：

- 当前后台鉴权、部分配置页、已有内容模型仍依赖现有用户体系
- 一次性删除风险过高，容易影响后台可用性

结论：

- 先禁用前台普通用户产品能力
- 后续再决定是否把后台认证独立化

### 决策 2：前端先做白名单路由

原因：

- 当前 `ui/src/router/routes.ts` 仍大量挂载社区路由
- 直接物理删页会增加联调成本

结论：

- 先把前台白名单路由收敛为文章/视频/项目/后台登录
- 其余路由统一下线或跳转 404

### 决策 3：后端 API 先做白名单暴露

原因：

- `internal/router/answer_api_router.go` 当前耦合面很大
- 直接删 controller/service/repo 风险高

结论：

- 优先收缩注册到 Router 的路由
- 后续再逐步清理 provider 和未使用模块

### 决策 4：点赞/评分做独立改造

原因：

- 当前 vote/reaction 体系默认与登录用户强耦合
- 产品上已明确不再要求登录

结论：

- 不在旧用户投票逻辑上继续硬改
- 单独定义匿名互动规则和 API

## 9. 分阶段交付

### 里程碑 M0：`ui-next` 独立运行

完成标准：

- `ui-next/` 可以本地独立启动
- 页面路由可以正常访问
- 已建立统一的 API 配置与请求基础层

### 里程碑 M1：`ui-next` 接通核心内容接口

完成标准：

- `ui-next` 的文章、视频、项目页面都能从现有后端取到真实数据
- 接口映射关系已经明确
- 新前端替换现有前端具备可行路径
### 里程碑 M2：前台内容门户化

完成标准：

- 前台导航仅展示文章、视频、项目
- 登录注册入口消失
- 问答、用户、徽章、评审等前台页面不再可达

### 里程碑 M3：后台内容运营化

完成标准：

- 后台菜单只保留内容运营相关页面
- 管理员仍可管理文章、视频、项目
- 用户、问答、徽章、评审相关后台入口不再暴露

### 里程碑 M4：接口最小化

完成标准：

- 前台只调用内容站所需 API
- 非必要公开 API 不再注册到公开路由

### 里程碑 M5：匿名互动改造

完成标准：

- 点赞/评分不依赖普通用户登录
- 前端能正常展示与提交互动数据

## 10. 验收标准

### 前台验收

- 首页和主导航只出现文章、视频、项目
- 访客访问 `/users/*`、`/review`、`/badges`、`/questions*` 时不可进入原页面
- Header 不显示登录、注册、通知、创建问题
- 页面文案不再出现社区问答语义

### 后台验收

- 管理员可登录后台
- 管理员可增删改文章、视频、项目
- 后台菜单不再出现 Questions、Answers、Users、Badges、Privileges、Review 等入口

### 接口验收

- 前端网络请求不再依赖 question/answer/user notification 等前台接口
- 管理后台接口仅保留当前页面真正使用的内容管理接口

## 11. 风险

### 风险 1：后台仍然依赖旧权限系统

处理：

- 第一阶段不动底层权限模型，只裁剪入口和页面

### 风险 2：文章可能仍沿用 question/content 模型

处理：

- 在 spec 执行时先确认文章的真实数据流，不要假定它已完全独立

### 风险 3：前台存在大量间接引用

处理：

- 先从路由、导航、service 导出收口
- 再处理残余页面和组件引用

### 风险 4：Swagger/Wire/生成文件同步问题

处理：

- 先改源码，再根据需要重生成 `docs/swagger.*` 和 `cmd/wire_gen.go`

## 12. 建议执行顺序

1. 跑通 `ui-next/`
2. 对接文章、视频、项目现有后端接口
3. 确认新前端页面数据流闭环
4. 前台路由与导航收口
5. Header 与登录注册入口移除
6. 后台菜单精简
7. 前端 service 白名单化
8. 后端公开路由白名单化
9. 点赞/评分匿名化改造
10. 再决定是否做深度物理清理
