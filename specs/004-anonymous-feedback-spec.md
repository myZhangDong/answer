# 004 匿名点赞与匿名评分 Spec

## 1. 背景

当前内容门户已经确认：

- 文章仍然复用 `question(content_type=2)` 链路
- 文章详情浏览量已经复用后端 `question.view_count`
- 内容门户不再面向普通用户提供注册、登录、个人中心等社区交互入口
- 点赞、评分需要从原有“登录用户社区行为”改为“匿名内容互动”

当前仓库内与本需求直接相关的现状是：

- 文章详情读取仍走 `GET /answer/api/v1/question/info`
- 文章列表读取仍走 `GET /answer/api/v1/content/page?content_type=2`
- 原后端已有 `vote` 体系，但它依赖登录用户、rank 权限、验证码和社区活动流
- `ui-next` 当前点赞与评分组件只是本地状态，没有真实后端持久化

因此需要拆出一份独立规格，明确“匿名点赞 + 匿名评分”在内容门户场景下的产品规则、接口边界、去重方式和数据结构，避免后续继续沿用旧社区 `vote` 逻辑。

## 2. 目标

### 2.1 产品目标

让访客在不登录的前提下，能够对文章进行点赞和评分，并看到聚合后的互动数据。

第一阶段必须满足：

- 访客无需登录即可点赞文章、视频、项目
- 访客无需登录即可为文章、视频、项目评分
- 前台展示三类内容的聚合点赞数
- 前台展示三类内容的聚合平均评分与评分人数
- 同一访客对同一内容对象的重复提交不会无限累加
- 前台不展示点赞用户或评分用户身份

### 2.2 工程目标

新增一套面向内容门户的轻量匿名互动模型，不继续复用旧社区的 `vote + rank + captcha + activity` 链路。

工程约束：

- 文章当前仍以 `question.id` 作为内容主键，不重做文章主模型
- 第一阶段同时覆盖文章、视频、项目三类内容
- 新接口与数据结构需要统一支持 `article / video / project`
- 不要求本轮彻底删除旧 `vote` 相关代码，但前台内容门户不再依赖它

## 3. 非目标

本规格不做以下事情：

- 不重构当前浏览量实现
- 不引入普通用户登录后再点赞的产品路径
- 不支持点踩
- 不支持带文本的评论式评分
- 不做复杂风控系统，只实现基础防刷与弱身份去重
- 不要求第一阶段清理所有旧 `vote_count` 历史数据来源

## 4. 现状确认

### 4.1 文章与浏览量现状

当前文章不是独立后端领域模型，而是 `question(content_type=2)` 的兼容实现。

现状：

- 文章列表来自 `/answer/api/v1/content/page?content_type=2`
- 文章详情来自 `/answer/api/v1/question/info?id=...`
- 文章详情请求会触发 `question.view_count` 自增

结论：

- 本规格第一阶段继续以“文章 = question(type=2)”为兼容前提
- 匿名互动记录中的 `object_id` 直接使用当前文章 ID，也就是 `question.id`

### 4.2 点赞现状

当前后端虽然存在通用 `vote` 能力，但不符合内容门户目标：

- `POST /answer/api/v1/vote/up`、`POST /answer/api/v1/vote/down` 依赖登录用户
- 投票会走 rank、验证码和社区活动通知链路
- `question.vote_count` 当前承载的是旧社区投票聚合值
- `ui-next` 文章详情页虽然展示“点赞数”，但按钮本身并未调用后端

结论：

- 旧 `vote` 只能视为历史兼容字段来源，不能直接作为匿名点赞方案
- 内容门户前台应改读新的匿名互动聚合结果

### 4.3 评分现状

当前仓库没有文章评分的后端实体、接口和存储模型。

结论：

- 评分需要完整新增后端能力
- `ui-next` 当前星级交互仅能作为视觉与交互参考，不能视为已实现

## 5. 范围

### 5.1 第一阶段覆盖对象

第一阶段同时覆盖：

- 文章详情页与文章列表页
- 视频详情页与视频列表页
- 项目详情页与项目列表页

说明：

- 三类内容的详情页都必须支持真实点赞和评分提交
- 列表页至少展示真实点赞数
- 列表页是否展示评分，第一阶段可选；如不展示，至少要保留详情页展示

### 5.2 点赞交互规则

默认规则如下：

1. 点赞只支持单向“点赞”，不支持点踩
2. 同一匿名访客对同一内容对象最多记一次点赞
3. 同一匿名访客再次发起点赞请求时直接拒绝
4. 第一阶段不支持取消点赞
5. 详情页需要支持跨会话恢复“我是否点过赞”
6. 前台读取接口需要返回当前访客点赞状态

说明：

- 点赞不支持取消，但需要恢复匿名访客的已点赞状态
- 前台按钮不能只依赖本地会话态，应以接口返回的游客状态为准

### 5.3 评分交互规则

默认规则如下：

1. 评分范围为 `1.0` 到 `5.0`
2. 评分步长为 `0.5`
3. 同一匿名访客对同一内容对象只能保留一条有效评分
4. 同一访客首次评分后，后续再次评分请求直接拒绝
5. 前台读取接口需要返回当前访客是否已评分以及其评分值

说明：

- 选择 `0.5` 步长，是为了兼容当前 `ui-next` 星级组件的交互形式
- 如果后续希望改成整数星级，可以在实现前回收为 `1~5` 整数，不影响整体架构

### 5.4 匿名身份与去重规则

第一阶段采用弱身份去重。

建议主方案：

- 以服务端签发的匿名 `cookie token` 作为主去重键
- 以 `IP hash + UA hash` 作为辅助风险信号

默认行为：

1. 首次提交点赞或评分时，如果请求中没有匿名 token，后端下发匿名 Cookie
2. 点赞唯一判定主键为：`object_type + object_id + anon_token`
3. 评分唯一判定主键为：`object_type + object_id + anon_token`
4. `IP` 和 `UA` 不作为主唯一键，但用于基础限流、异常检测和追查

说明：

- 只用 `IP + UA` 去重会误伤同一网络环境下的正常用户
- 只用 Cookie 会弱一些，但对内容门户的轻互动场景足够实用
- 第一阶段不追求强实名、防高级刷量，只追求“低成本、可上线、可扩展”

### 5.5 聚合数据展示规则

第一阶段前台需要消费以下聚合值：

- `like_count`
- `rating_avg`
- `rating_count`

展示建议：

- `like_count` 为整数
- `rating_avg` 保留一位小数
- `rating_count` 为整数
- 当 `rating_count = 0` 时，前台展示“暂无评分”
- 第一阶段列表页不展示评分，只展示点赞数

## 6. 历史数据兼容策略

第一阶段默认不做历史点赞数兼容。

明确结论：

- 不迁移现有 `question.vote_count`
- 新匿名互动统计从 0 开始累计
- 线上旧点赞数即使归零也可以接受

说明：

- 这样可以减少迁移脚本、懒初始化和历史口径混算的复杂度
- 评分本来就没有历史字段，因此不存在兼容问题

## 7. API 策略

### 7.1 公开读取接口

第一阶段建议同时采用“两层读取”：

#### A. 文章原详情/列表接口继续保留主体内容

- `GET /answer/api/v1/content/page`
- `GET /answer/api/v1/question/info`

#### B. 新增匿名互动聚合读取接口

建议新增：

- `GET /answer/api/v1/content/feedback`

建议入参：

```json
{
  "object_type": "article",
  "object_id": "123456"
}
```

建议返回：

```json
{
  "object_type": "article",
  "object_id": "123456",
  "like_count": 128,
  "rating_avg": 4.5,
  "rating_count": 37,
  "liked_by_me": true,
  "rated_by_me": true,
  "my_rating": 4.5
}
```

说明：

- 第一阶段详情页需要读取当前匿名访客操作态
- 如果后续首页/列表页也需要大量展示互动统计，可再补批量查询接口

### 7.2 点赞提交接口

建议新增：

- `POST /answer/api/v1/content/feedback/like`

建议请求体：

```json
{
  "object_type": "article",
  "object_id": "123456"
}
```

建议返回：

```json
{
  "object_type": "article",
  "object_id": "123456",
  "like_count": 129,
  "rating_avg": 4.5,
  "rating_count": 37,
  "liked_by_me": true,
  "rated_by_me": false,
  "my_rating": 0
}
```

默认行为：

- 如果该匿名访客此前已点过赞，则本次请求直接拒绝
- 首次成功后返回最新聚合值和当前访客状态

### 7.3 评分提交接口

建议新增：

- `POST /answer/api/v1/content/feedback/rating`

建议请求体：

```json
{
  "object_type": "article",
  "object_id": "123456",
  "rating": 4.5
}
```

建议返回：

```json
{
  "object_type": "article",
  "object_id": "123456",
  "like_count": 129,
  "rating_avg": 4.6,
  "rating_count": 38,
  "liked_by_me": true,
  "rated_by_me": true,
  "my_rating": 4.5
}
```

默认行为：

- 首次评分新增 `rating_count`
- 同一匿名访客再次评分时直接返回错误，不允许修改旧评分

### 7.4 与旧 `vote` 接口的关系

内容门户前台不再依赖：

- `POST /answer/api/v1/vote/up`
- `POST /answer/api/v1/vote/down`

说明：

- 旧接口继续保留给旧社区链路或兼容逻辑，不在本规格中删除
- `ui-next` 和内容门户公开页面统一切到新匿名互动接口

## 8. 数据结构建议

### 8.1 建议新增聚合表

建议新增一张聚合统计表，例如：

- `content_feedback_stat`

建议字段：

- `object_type`
- `object_id`
- `like_count`
- `rating_sum`
- `rating_count`
- `rating_avg`
- `created_at`
- `updated_at`

说明：

- `rating_avg = rating_sum / rating_count`
- `rating_sum` 用于避免每次重算全表

### 8.2 建议新增匿名记录表

建议新增一张匿名访客互动记录表，例如：

- `content_feedback_record`

建议字段：

- `object_type`
- `object_id`
- `anon_token_hash`
- `liked`
- `rating_value`
- `last_ip_hash`
- `last_ua_hash`
- `created_at`
- `updated_at`

建议唯一键：

- `(object_type, object_id, anon_token_hash)`

说明：

- 同一匿名访客对同一对象只保留一条互动记录
- 一条记录同时承载“是否点赞”和“评分值”，避免拆两张表造成写路径分裂

### 8.3 数据一致性建议

写入流程建议放在同一事务内：

1. 读取或创建匿名记录
2. 判断本次点赞/评分是否会改变状态
3. 更新记录表
4. 回写聚合表

建议保留一个后台修复能力：

- 支持按对象重算聚合值
- 便于后续排查异常统计或迁移错误

## 9. 前端接入策略

### 9.1 `ui-next` 接入原则

`ui-next` 需要从“本地假交互”切到真实后端：

- 文章、视频、项目详情页都不再只读旧字段或本地假数据
- 点赞按钮点击后调用新点赞接口
- 评分星级提交后调用新评分接口
- 成功后用接口返回的聚合值刷新页面

### 9.2 展示策略

第一阶段建议：

- 文章、视频、项目详情页展示真实 `like_count`
- 文章、视频、项目详情页展示真实 `rating_avg` 与 `rating_count`
- 文章、视频、项目详情页展示并恢复当前匿名访客是否已点赞、是否已评分
- 无评分时显示“暂无评分”
- 文章、视频、项目列表页至少切换到真实 `like_count`
- 文章、视频、项目列表页第一阶段不展示 `rating_avg` 与 `rating_count`

### 9.3 失败与容错

建议前端按以下原则处理：

- 互动接口失败时，保留当前页面主体可读，不影响正文展示
- 点赞/评分失败时给出轻提示，不阻断页面
- 不因匿名 token 缺失而让前端先做额外初始化请求

## 10. 风控与限流

第一阶段只做基础防护。

建议至少包含：

- 按 `IP` 的基础限流
- 按 `anon_token` 的基础限流
- 对短时间内连续命中的同一对象提交做幂等或抖动保护
- 对异常高频的 `IP + UA` 组合记录日志

本轮明确不做：

- 复杂设备指纹
- 人机验证挑战
- 黑产对抗级风控平台

## 11. 实施建议

建议拆三步推进。

### Phase A：后端匿名互动基础能力

目标：

- 完成数据表、schema、repo、service、controller、router
- 跑通文章、视频、项目的聚合读取、点赞提交、评分提交

### Phase B：`ui-next` 前台详情接入

目标：

- `ui-next` 文章、视频、项目详情从真实接口读取互动数据
- 替换当前本地点赞和评分逻辑

### Phase C：列表与兼容收口

目标：

- 首页和三类内容列表页改读真实点赞聚合值
- 明确新互动统计从 0 开始累计
- 检查三类内容前台展示口径一致

## 12. 已确认细节

- 第一阶段列表页不展示评分，只展示点赞数
- 匿名 `token` 默认有效期先设置为 3 个月
- 首页热门内容排序第一阶段不引入评分维度，只和浏览次数有关

## 13. 当前无新增开放问题

如后续希望把评分引入首页热门排序，需作为新决策单独确认，不在 `004` 第一阶段范围内处理。
